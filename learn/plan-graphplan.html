Week 8 · Planning

Graphplan

Run it step by step

Graphplan builds a layered graph in polynomial time that over-approximates what can be true after each number of steps, then does a much smaller backward search inside it. The graph alternates proposition layers P0, P1, … and action layers A0, A1, …. A no-op (persistence) action carries each proposition unchanged to the next layer. Mutex pairs record things that can never hold together (propositions) or be done together (actions) at that level.

⎙Tip: press Ctrl+P to print or save this page as PDF.

01Definition

Layer P0 is the initial state. Action layer Ai holds every action whose preconditions are all in Pi and pairwise non-mutex, plus a no-op for each proposition. Pi+1 holds every add effect. Two actions in the same layer are mutex by: (1) inconsistent effects, one adds what the other deletes; (2) interference, one deletes a precondition of the other; (3) competing needs, a precondition of one is mutex with a precondition of the other in Pi. Two propositions in Pi+1 are mutex by inconsistent support: every pair of actions that achieve them is mutex. When all goals are in a layer and pairwise non-mutex, extract a plan backwards: choose a set of non-mutex actions achieving the goals, make their preconditions the subgoals one layer earlier, and repeat; a goal set that fails at a layer is remembered as a nogood. Actions in one layer are mutually non-mutex so they may be done in any order, which gives the flat plan.

02Pseudocode

P0 ← initial state;  i ← 0
loop
    if all goals ∈ Pi and no two goals are mutex in Pi:
        plan ← EXTRACT(goals, i);  if plan ≠ failure: return plan
    if graph has levelled off and nogoods stopped growing: return failure
    Ai ← actions whose preconditions are in Pi and pairwise non-mutex, plus a no-op for every proposition
    mark action mutexes: inconsistent effects, interference, competing needs
    Pi+1 ← all add-effects of Ai
    mark proposition mutexes: inconsistent support (every pair of achievers is mutex)
    i ← i + 1

EXTRACT(G, i):  if i = 0 return [ ]
    if G ∈ nogood(i) return failure
    choose non-mutex actions in Ai−1 that achieve every g ∈ G (try no-ops first)
    G' ← union of their preconditions;  plan ← EXTRACT(G', i−1)
    if none works: add G to nogood(i); return failure

04Formulas and why they hold

p, q mutex in Pi+1 ⇔ every achiever of p is mutex with every achiever of q

inconsistent support

If no non-mutex pair of actions can make both, they cannot both be true after that step.

a, b mutex ⇐ add(a) ∩ del(b) ≠ ∅ or del(a) ∩ pre(b) ≠ ∅ or pre(a) and pre(b) contain a mutex pair

inconsistent effects, interference, competing needs

Each rule names a way the two actions cannot both be carried out in one parallel step.

05Why it works, and when it does not

Mutex reasoning prunes huge numbers of impossible combinations cheaply before any search, and the first layer in which the goals are non-mutex is a lower bound on the plan length (the plan returned has the fewest layers).

06Properties

completeyes (finds a plan whenever one exists)

07Traps

  • Goals appearing without mutex is necessary, not sufficient: extraction can still fail and the graph must be extended.
  • A no-op is an action: it can be mutex with real actions (for example a no-op that keeps AE true is mutex with any action that deletes AE).
  • Layers count parallel steps; in the one-arm blocks world nearly every pair of actions is mutex, so layers and plan steps coincide.
  • Nogoods are goal sets proved unachievable at a layer: a repeat visit is cut immediately instead of searched again. Try example plan-graphplan-nogoods: the goals are non-mutex at P4 but extraction fails at P4 and P5 and succeeds at P6, reusing nogoods.
  • The termination test (graph levelled off and the nogood table at the layer where it levelled stopped growing) proves that no plan exists; it is checked after every failed extraction.
