Backward chaining (goal tree)

Run it step by step

Forward chaining starts from the facts and derives everything it can. Backward chaining starts from a query (the goal) and works the other way: which rule could conclude this, and what would I then have to show? Only rules relevant to the goal are ever examined, which is why it suits diagnosis and question answering.

⎙Tip: press Ctrl+P to print or save this page as PDF.

01Definition

To prove a goal G: (1) if some fact unifies with G, G is solved; (2) otherwise, for each rule whose THEN part unifies with G, make each IF condition a sub-goal. The conditions of one rule form an AND connector (all must be proved); the different rules that could conclude G are OR alternatives. Variables are bound by unification and the bindings are carried from one condition to the next. This is the same AND–OR structure as in problem decomposition.

02Pseudocode

Prove(goal, bindings):
    for each fact f that unifies with goal: succeed (f is a solved leaf)
    for each rule R whose consequent unifies with goal:        # OR over rules
        prove every condition of R in turn, carrying the bindings   # AND over conditions
        if all succeed: goal is proved by R
    if nothing works: goal fails (backtrack to the last choice)
    (a goal identical to one of its own ancestors fails: it would loop)

03Line by line

goal: look for a matching factA fact that unifies with the goal is a solved leaf.
otherwise find rules whose consequent matchesEach such rule is an alternative (OR).
sub-goal on every antecedent of the ruleAll conditions must be proved (AND), left to right, sharing variable bindings.
backtrack on failureIf a goal cannot be proved, undo the last choice and try the next fact or rule.

04Formulas and why they hold

solved(G) = fact(G) ∨ ⋁ over rules R concluding G of ⋀ solved(c), c in IF(R)

a goal is solved by a fact, or by some rule all of whose conditions are solved

OR across the alternative rules and AND across the conditions of one rule is exactly an AND–OR graph.

05Why it works, and when it does not

Every goal it proves is also derived by forward chaining (both are sound), but it only does the work needed for the query. An ancestor check is needed because rule bases can be recursive.

06Properties

completeno for recursive rule bases (depth-first), yes on acyclic ones
optimaln/a
timeexponential in the worst case
spacethe goal tree (depth × branching)

07Traps

  • The first matching fact or rule is not always the right one: bindings may make a later condition fail, and then it must backtrack. Try example rules-backtrack: rule F1 fails on (heavy tweety), the grey branch is undone, and F2 proves the goal.
  • Rule variables are renamed apart for each use, so ?x in two different uses are different variables.
  • Without the ancestor check a recursive rule (ancestor defined through ancestor) can loop forever.
  • This stepper proves the first answer found; a query with variables may have several answers.
