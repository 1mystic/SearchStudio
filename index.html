    Guide
    
  
    How to use Search Studio
    
  
    Three places matter: the library, where you learn an algorithm; the studio, where you run it; and the export panel, where you take the trace away.
    

  
    1. Learn the algorithm first
    
  
    Open the library and pick an algorithm. Its page has:
    
  
      
    
    • Introduction in plain language, and a precise definition.
      • 
    
    • Pseudocode with a sentence on what each line does and why.
      • 
    
    • Formulas: each written out, read aloud in words, and justified.
      • 
    
    • Properties (complete? optimal? time and space) and common traps.
      • 
  
    
  
    Press Try it to open the studio with that algorithm and a suitable example already loaded.
    

  
    2. Run it in the studio
    
  
    Choose a problem
    
  
      
    
    • Examples come with the site: the six-city instance from the TSP deck, two five-city practice matrices, and three graphs for uninformed and informed search.
      • 
    
    • Random makes a new TSP or graph from a size and a seed. The same seed always gives the same problem, so you can share it.
      • 
    
    • Edit shows the problem as text you can change (format below) and saves it under My problems in this browser.
      • 
    
    • Import accepts a problem as JSON (paste it or choose a file); Export problem gives you that JSON back.
      • 
  
    
  
    Choose an algorithm and its settings
    
  
    Only algorithms that fit the problem type are listed. Settings such as start city, beam width, tabu tenure, temperature or random seed appear below. Changing anything re-runs the algorithm from the start.
    
  
    Step through
    
  
      
    
    • ← → step back and forward, Space plays or pauses, Home / End jump to the first or last step.
      • 
    
    • The slider scrubs; the speed menu sets seconds per step.
      • 
    
    • The Trace tab lists every step's caption; click one to jump to it.
      • 
  
    

  
    3. Read the stage
    
  
    Left: the graph. Right: the working table for this algorithm, with the current row highlighted, and a small chart where one helps (temperature runs, restarts, roulette wheels). Below: the lists, such as OPEN and CLOSED written as node pairs (node, parent, value). At the bottom, in yellow, one sentence says what just happened.

    4. Problem text formats
    
  
    TSP: names, then the matrix
    

    A B C D E
0 58 92 34 81
58 0 20 46 70
92 20 0 28 53
34 46 28 0 12
81 70 53 12 0
    
  
    Use any whitespace or commas. The matrix may be asymmetric; the site tells you when it is.
    
  
    Graph: start, goal, heuristic, edges
    

    start S
goal G
undirected
h S 7
h A 5
# edges: from to cost
S A 2
S B 5
A G 6
B G 1
    
  
    Write directed instead of undirected for one-way edges. Lines starting with # are comments. Nodes without a position are placed on a circle.
    

  
    5. Take it away
    
  
      
    
    • Printable trace: a self-contained HTML page with a cover (problem, settings, pseudocode) and one step per printed page. Open it in a browser and print, or save as PDF.
      • 
    
    • Trace JSON / CSV: every step's caption, table and lists, for notes or spreadsheets.
      • 
    
    • Current step as SVG: the graph drawing, for slides.
      • 
  
    

  
    Conventions used everywhere
    
  
      
    
    • Ties are broken alphabetically unless a setting says otherwise; MoveGen lists neighbours alphabetically.
      • 
    
    • Tours are written in path representation; the edge back to the start is always included in the cost.
      • 
    
    • Graph search is graph search: a node already on OPEN or CLOSED is not added again; UCS and A* update it when they find a cheaper path.
      • 
    
    • The goal test happens when a node is picked from OPEN, as in the course.
      • 
    
    • Random choices use a seeded generator, so a run can always be repeated exactly.
      • 
  
    

    

    
  
    

    
  
    About
    
  
    About Search Studio
    
  
    A free, public-domain study companion for AI: Search Methods for Problem Solving (Prof. Deepak Khemani, IIT Madras). Every algorithm in the course is traced step by step, exactly the way it is traced by hand.
    

  
    Why it exists
    
  
    Search algorithms are easy to describe and surprisingly easy to trace wrongly. A missed tie-break, a child added twice or a savings pair merged that should have been refused will all give a wrong answer. Seeing every step, with the working table and the OPEN and CLOSED lists side by side, makes those mistakes visible.
    

  
    Full syllabus
    
  
    Weeks 1–11 of the course, with the algorithms you can run for each week. Every week also has its own section on the course map.
    

  
    Week 1 · Introduction and philosophy
    
  
      
    
    • Introduction: what artificial intelligence is and where search fits in.
      • 
    
    • Philosophy: the Turing Test and the Winograd Schema Challenge.
      • 
    
    • No algorithms to run this week.
      • 
  
    

  
    Week 2 · State space search
    
  
      
    
    • Introduction to state space search: states, MoveGen, GoalTest, and the search space as a graph.
      • 
    
    • Examples of state spaces.
      • 
    
    • Depth First Search (DFS) and Breadth First Search (BFS), with OPEN and CLOSED as lists of node pairs.
      • 
    
    • Depth First Iterative Deepening (DFID).
      • 
    
    • Analysis: completeness, the path found, time and space.
      • 
    
    • In the studio: BFS · DFS · DFID
      • 
  
    

  
    Week 3 · Heuristic search and local search
    
  
      
    
    • Heuristic search: Best First Search, Hill Climbing and Beam Search on graphs.
      • 
    
    • Solution space search: the travelling salesperson problem (TSP).
      • 
    
    • Constructive TSP methods: Nearest Neighbour, Greedy and Savings, with brute force as the exact reference.
      • 
    
    • Perturbation methods: 2-city exchange, 2-edge exchange (2-opt), Or-opt, 3-edge exchange.
      • 
    
    • Escaping local optima: Variable Neighbourhood Descent, Beam Search, Tabu Search.
      • 
    
    • Stochastic local search: Iterated Hill Climbing, Random Walk, Simulated Annealing.
      • 
    
    • In the studio: Best First · Hill Climbing · Beam Search · Nearest Neighbour · Greedy · Savings · Brute force · 2-city exchange · 2-opt · Or-opt · 3-edge exchange · VND · Beam (TSP) · Tabu · Iterated HC · Random walk · Simulated annealing
      • 
  
    

  
    Week 4 · Population based methods
    
  
      
    
    • Genetic Algorithms: selection, crossover and mutation.
      • 
    
    • TSP crossovers: cycle (CX), partially mapped (PMX), order (OX), alternating edges (AEX), heuristic (HX) and ordinal.
      • 
    
    • Emergent systems.
      • 
    
    • Ant Colony Optimisation: pheromone, evaporation and the probabilistic tour rule.
      • 
    
    • In the studio: Genetic algorithm · Crossover lab · Ant colony
      • 
  
    

  
    Week 5 · Finding optimal paths
    
  
      
    
    • Branch and bound and Uniform Cost Search (UCS).
      • 
    
    • Algorithm A*: f(n) = g(n) + h(n), and weighted A*.
      • 
    
    • Admissibility of A*: if h never overestimates, the first goal picked is optimal.
      • 
    
    • In the studio: UCS · A*
      • 
  
    

  
    Week 6 · Monotone condition and saving space
    
  
      
    
    • The monotone (consistency) condition: h(n) ≤ k(n, m) + h(m).
      • 
    
    • Space-saving versions of A*: IDA*, Recursive Best-First Search, Divide and Conquer Frontier Search.
      • 
    
    • Sequence alignment as shortest-path search, by dynamic programming and by A*.
      • 
    
    • In the studio: Admissibility & monotone check · IDA* · RBFS · DCFS · Alignment (DP) · Alignment (A*)
      • 
  
    

  
    Week 7 · Game playing
    
  
      
    
    • Game theory and board games: game trees, MAX and MIN, evaluation functions.
      • 
    
    • Minimax.
      • 
    
    • Alpha-Beta pruning, and why node ordering matters.
      • 
    
    • SSS*: best-first search over strategies.
      • 
    
    • In the studio: Minimax · Alpha-Beta · SSS*
      • 
  
    

  
    Week 8 · Planning
    
  
      
    
    • Domain-independent planning in the blocks world: STRIPS operators, preconditions, add and delete lists.
      • 
    
    • Forward and backward state-space planning.
      • 
    
    • Goal Stack Planning, and the Sussman anomaly.
      • 
    
    • Plan Space Planning: Partial Order Planning.
      • 
    
    • In the studio: Forward planning · Backward planning · Goal Stack Planning · Partial Order Planning
      • 
  
    

  
    Week 9 · Problem decomposition
    
  
      
    
    • Problem decomposition with goal trees.
      • 
    
    • AND–OR graphs: hyper-arcs, solved nodes and futility.
      • 
    
    • Algorithm AO*: forward expansion, backward cost revision, the marked solution graph.
      • 
    
    • In the studio: AO*
      • 
  
    

  
    Week 10 · Rule-based expert systems
    
  
      
    
    • Rule-based expert systems and pattern-directed inference.
      • 
    
    • The inference engine: match, resolve, execute. Conflict resolution strategies.
      • 
    
    • The Rete algorithm: a network that remembers partial matches.
      • 
    
    • In the studio: Forward chaining · Rete
      • 
  
    

  
    Week 11 · Constraint processing
    
  
      
    
    • Constraint satisfaction problems: variables, domains, binary constraints.
      • 
    
    • Backtracking and forward checking with variable-ordering heuristics.
      • 
    
    • Arc consistency (AC-1, AC-3).
      • 
    
    • Combining search and reasoning.
      • 
    
    • The Waltz algorithm: labelling line drawings of trihedral objects.
      • 
    
    • Model-based diagnosis: conflicts and minimal diagnoses.
      • 
    
    • In the studio: Backtracking · Forward checking · Arc consistency · Waltz · Model-based diagnosis
      • 
  
    

  
    Notation
    
  
    The site follows the notation of the course and of Prof. Khemani's book A First Course in Artificial Intelligence:
    
  
      
    
    • MoveGen and GoalTest.
      • 
    
    • OPEN and CLOSED as lists of node pairs (node, parent, depth or g).
      • 
    
    • Ties broken alphabetically.
      • 
    
    • The goal test applied when a node is picked from OPEN.
      • 
    
    • The path representation for tours.
      • 
    
    • The sigmoid acceptance rule for simulated annealing.
      • 
    
    • The course's crossover conventions.
      • 
  
    
  
    It is an independent study aid, not affiliated with or endorsed by IIT Madras or NPTEL.
    

  
    How results are checked
    
  
    On each build, every algorithm runs against every example and against random problems.
    
  
      
    
    • Tours must be permutations, and the reported cost must match a fresh recomputation. Paths must run from start to goal at the cost reported.
      • 
    
    • IDA*, RBFS and DCFS must find the same cost as UCS.
      • 
    
    • Minimax, Alpha-Beta and SSS* must give the same value.
      • 
    
    • Every plan must execute in the blocks world.
      • 
    
    • Rete must derive the same facts as forward chaining.
      • 
  
    
  
    The six-city TSP results also match an independent Python implementation: optimum 224, Nearest Neighbour 264, Greedy 238, Savings 224.

    Use your own problem, no code needed
    
  
      
    
    1. In the studio, open the problem card and choose Import.
      2. 
    
    2. Paste JSON that follows the importing guide, or choose a .json file.
      3. 
    
    3. The problem is saved under My problems in this browser. You can share it with Export & print → Export problem.
      4. 
  
    
  
    The quickest way to make a new problem is to export a built-in example of the same kind, change the values, and import it again.

    Project layout
    

    SearchStudio/
├── algorithms/          one file per algorithm, grouped by folder
│   ├── _template.js     copy this to start (files starting with _ are skipped)
│   ├── search/  tsp/  alignment/  games/  andor/  planning/  rules/  csp/
├── problem-types/       how each kind of problem is drawn, typed and generated
├── examples/            one JSON file per built-in problem
├── IMPORTING.md         JSON schemas for every problem type
├── src/
│   ├── core/            registry, problem model, search engine, TSP helpers
│   ├── ui/              stage renderer and the app
│   ├── pages/           home, guide, about, contribute (plain HTML)
│   └── styles/          studio.css
├── tools/
│   ├── build.mjs        scans the folders and builds the site, learn pages, sitemap, llms.txt
│   └── test.mjs         runs every algorithm on every example, checks known answers
├── index.html           generated: the site
└── dist/SearchStudio.html   generated: the whole site in one file
    

  
    Add an algorithm in four steps
    
  
      
    
    1. Copy algorithms/_template.js to algorithms/<folder>/<name>.js.
      2. 
    
    2. Fill in the metadata (id, name, family, week, problem), the learn block, params and run.
      3. 
    
    3. Run npm run build (or npm run watch while you work). The build loads every file, checks that it registers, runs it on the examples and on random problems, and regenerates the site.
      4. 
    
    4. Open the site and find your algorithm in the library and on the course map.
      5. 
  
    

  
    The algorithm file
    

    Studio.register({
  id: "tsp-my-method",            // unique, used in links: #algo-tsp-my-method
  name: "My method",
  family: "TSP · local search",   // the library groups by this
  week: 3,                        // course week 1–11: places it on the course map
  problem: "tsp",                 // tsp, graph, game, andor, planning, rules, csp, linedrawing, circuit, alignment
  order: 200,                     // position inside the family
  summary: "One sentence for the library card.",
  pseudocode: `...`,
  complexity: "O(n²) per step",
  learn: {
    intro: "Plain-language introduction.",
    definition: "Precise definition.",
    steps: [["pseudocode line", "what it does and why"]],
    formulas: [{ f: "formula", read: "in words", why: "why it holds" }],
    why: "When it works and when it fails.",
    traps: ["Common mistake"],
    props: { complete: "no", optimal: "no", time: "…", space: "…" }
  },
  params: [
    { key: "start", label: "Start city", type: "city", default: P => P.ids[0] },
    { key: "w", label: "Beam width", type: "int", default: 2 },
    Studio.seedParam(1)
  ],
  run(P, params) {
    // P.ids, P.d(a, b), P.cost(tour) for TSP; P.adj, P.h, P.start, P.goal for graphs
    return { steps: [ /* one object per snapshot */ ], result: { tour, cost } };
  }
});
    

  
    What a step can contain
    
  
    
    
    fieldshapeshown as
    
    
      
    captionstringthe yellow sentence under the stage (required)
    
      
    nodes{ A: { state, badge, label, sub } }node colours. States: plain, current, open, closed, visited, path, goal, start, rejected, pruned, dim
    
      
    edges[{ u, v, state, label, directed }]edges. States: faint, tour, path, candidate, added, removed, rejected, alt, tree, pheromone, boundary
    
      
    table{ title, columns, rows, rowStates }the working table. Row states: ok, bad, warn, cur, dim. A cell may be { t, s }
    
      
    lists[{ label, items: [{ text, state }] }]OPEN and CLOSED rows, populations, agendas
    
      
    stats[{ label, value, state }]the numbers under the drawing
    
      
    chart{ kind: walk | drops | bars | pie, … }cost curves, roulette wheels, probability bars
    
      
    scene / blockscustom layout / blocks-world stackstrees, lattices, line drawings, the blocks world

    House rules
    
  
      
    
    • Follow the course notation: node pairs (N, parent, depth or g), and the goal test when a node is picked from OPEN.
      • 
    
    • Ties are broken the course's way (alphabetically), unless a setting says otherwise.
      • 
    
    • Every caption says why the step happened, not just what happened.
      • 
    
    • The learn block explains every formula you use and at least one trap.
      • 
    
    • Random choices go through Studio.rng(seed) so runs repeat exactly.
      • 
    
    • Add a known answer to tools/test.mjs when the course gives one.
      •
